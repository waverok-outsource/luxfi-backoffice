# 19. Support Tickets & Password Reset Requests API Integration

## Status

Accepted — 2026-08-11. Design complete, contracts confirmed via `luxfi.postman_collection.json`. Handoff to DeepSeek written in `docs/implementation.md`, implemented, reviewed, and live-tested against production. The frontend build is correct against the API's actual behavior; live testing surfaced two **backend** defects (not frontend issues) that block real usage of two flows — see [bug report 0001](../bug-reports/0001-support-tickets-backend-issues.md).

## Decision

Wire three currently-mocked surfaces to the real backend, all backed by the `Support` resource confirmed in the Postman collection:

- **Help & Support module** (`/help-support`, ADR 0014) — both tabs: **Support Tickets** (`GET /v1/support/tickets`, admin-wide) and **Password Reset Requests** (`GET /v1/support/password-reset-requests`).
- **Customer detail's embedded Support Tickets tab** (`/customers/[id]`, ADR 0006) — `GET /v1/customers/:customerId/support-tickets`, the same ticket resource scoped to one customer.

These are three separate UI surfaces but only **two backend resources** (tickets, password-reset-requests) and **one shared review mutation** for tickets (`PATCH /v1/support/tickets/:ticketRef`) used by both the admin-wide table and the customer-embedded panel — a ticket is reviewed the same way regardless of which screen it was opened from.

Key design calls:

- **One `SupportTicketType` and one `reviewSupportTicket` mutation serve both ticket surfaces.** Two separate `fetch*` functions exist only because the two list endpoints have different URLs and scoping (`fetchSupportTickets(query)` for the admin-wide table, `fetchCustomerSupportTickets(customerId, query)` for the embedded tab) — everything downstream (type, row mapping, review mutation, status config) is shared.
- **Password reset requests stay admin-only this round** — there's no customer-embedded password-reset tab in the current UI, so only the Help & Support module's tab is wired. `POST /v1/customers/:customerId/password-reset-requests` (customer-initiated creation) is not wired anywhere; nothing in either admin surface creates a request, only reviews existing ones.
- **Create-ticket and ticket-categories are out of scope.** `POST /v1/customers/:customerId/support-tickets` and `GET /v1/support/ticket-categories` are confirmed endpoints, but neither admin surface has a "create ticket" UI today (tickets are created by customers via the mobile/web app) — wiring them now would be building UI nobody asked for.
- **Ticket review PATCH body is inferred, not sampled.** The Postman example for `PATCH /v1/support/tickets/:ticketRef` has an empty request body — only the response is captured (showing `status` flip from `"pending"` to `"resolved"` and a new `resolvedAt` field). The existing UI (a single "Mark Issue as Resolved" switch, no reason field ever collected on this flow) implies a binary `{ status: "resolved" }` payload. This mirrors the ADR 0018 precedent for unsampled response shapes — flagged with an `ASSUMPTION` comment in the code, same convention as `updateAsset`/`deleteAsset` in `asset-management.fns.ts`. **Update, 2026-08-11:** live testing sent exactly this inferred body (`{"status":"pending"}`) and the backend rejected it with `400 "Please, provide a value for status"` — the inferred shape may still be wrong, or the backend validator has a bug; this is now tracked as [bug report 0001, Bug 2](../bug-reports/0001-support-tickets-backend-issues.md#bug-2-ticket-review-patch-rejects-a-validly-populated-status-field) rather than left as an open assumption.
- **Password reset review POST body is empty — confirmed, not assumed.** The Postman request for `POST /v1/support/password-reset-requests/:passwordchangeref` has no body and the existing "Reset User Password" button already takes no form input, just fires a confirm action. No payload to send.
- **The customer-scoped ticket list's response shape was ambiguous and needed a live check before sign-off — now verified.** Both Postman samples for `GET /v1/customers/:customerId/support-tickets` return a bare single ticket object — no array, no `pagination` wrapper — unlike every other list endpoint in this codebase, including the sibling `GET /v1/support/tickets` which *does* return `data: [...]` + `pagination`. Building against `PaginatedApiResponse<SupportTicketType[]>` (consistent with the rest of the codebase) was the decision here. **Update, 2026-08-11:** live-tested against production — the real endpoint returns the full paginated-array envelope, confirming the Postman samples were an incomplete capture, not the real contract. No code change needed; this risk is closed. However, live testing surfaced a separate, unrelated defect — the endpoint returns an empty list for a customer who has real tickets attributable to them by email/phone — tracked as [bug report 0001, Bug 1](../bug-reports/0001-support-tickets-backend-issues.md#bug-1-customer-scoped-ticket-list-doesnt-return-tickets-that-belong-to-the-customer).
- **Status types stay as the exact two-value unions the existing mock UI already assumes** (`"pending" | "resolved"` for tickets, `"pending" | "reset"` for password resets) rather than widening to a free-form string. `createStatusColumn`'s existing fallback (render `-` for any value not in the config) already handles an unanticipated third status value safely, so there's no correctness risk in keeping the narrower, more useful type.
- **`channel` arrives lowercase from the API** (`"web"`, `"mobile"`) while the mock UI's type is a capitalized union (`"Web" | "Mobile"`). This is display formatting, not a data-shape problem — capitalize at render time, don't change the API type.
- **Metrics stay hardcoded.** `GET /v1/support/stats` is a confirmed endpoint but its example response is empty in the collection — no shape to build against. The three `HelpSupportMetrics` cards are an explicit, separate backend dependency, unchanged by this integration (same treatment ADR 0018 gave Marketplace's aggregate metrics).
- **The two near-duplicate UI implementations (admin `support-tickets-table.tsx` vs. customer-embedded `support-tickets-panel.tsx`) are wired independently, not merged.** They already existed as separate component trees before this integration; de-duplicating them into one shared component is a real refactor with its own risk and isn't part of getting them off mock data.

## Context

`docs/STATUS.md` listed Help & Support as fully mocked with all backend endpoints "Unknown." The newly-added `luxfi.postman_collection.json` (2026-08-11) turns out to fully confirm this module, plus the previously-undocumented Support Tickets tab embedded in the Customer detail page (that tab existed in the codebase — `customer-details/components/support/`, seven tabs total on that page — but wasn't captured in ADR 0006, which only documented three of the seven).

This is the first of a sequenced set of API-integration passes prompted by the same Postman collection; Customer Module (remaining tabs: KYC, Asset Portfolio, Asset Loans) and the Loan Module are follow-up phases, chosen to go after this one because Support Tickets has the cleanest, most-fully-sampled contract of the three and no data-model mismatches to design around (unlike KYC, which needs a tier-model redesign — see the Customer Module follow-up ADR).

## Alternatives Considered

- **Wire `GET /v1/customers/:customerId/support-tickets` as a single-object response**, matching the Postman example literally instead of assuming a list. Rejected for now — every other list-shaped endpoint in this codebase (including the sibling general endpoint) returns `PaginatedApiResponse<T[]>`, and a customer support-tickets tab that can only ever show one ticket would be a strange product decision with no stated rationale. Treated as a probable incomplete Postman capture rather than a real API design choice; flagged for live verification rather than guessed around silently. **Confirmed correct** by live testing 2026-08-11 — see Decision section above.
- **Merge the admin and customer-embedded ticket tables into one shared component now.** Rejected — out of scope for an API-wiring pass; the two already have divergent UI shells (different modal designs, different toolbar components) that would need real reconciliation work, not just data-source swapping.
- **Send the inferred `{ status: "resolved" }` review payload with a reason/comment field anyway**, in case the backend silently accepts extra fields. Rejected — same reasoning ADR 0018 used for the marketplace's rejection reason: asserting an untested field into a request is worse than sending exactly what's confirmed and expanding later once the backend confirms it accepts more.
