# 20. Customer Detail — Asset Portfolio & Asset Loans API Integration

## Status

Accepted — 2026-08-11. Built by DeepSeek, reviewed, and live-tested against production. `tsc`/lint clean. One flagged assumption was live-tested and found **wrong** (fixed directly, see below); the remaining three could not be live-tested this round because no pending asset or open loan existed anywhere in the current backend data to exercise them against — they remain open until a suitable test case exists.

## Decision

Wire two of the customer detail page's remaining mocked tabs ([ADR 0006](0006-customers.md) / [ADR 0019](0019-support-tickets-api-integration.md) note this page has 7 tabs total): **Asset Portfolio** (`asset-portfolio-panel.tsx`) and **Asset Loans** (`asset-loans-panel.tsx`). KYC & Compliance is deferred to its own ADR — it needs a data-model redesign (fixed 3-document/Tier-2 mock vs. the real dynamic tier+submission model), a materially different kind of work than these two. Transactions History and Smart Contracts stay mocked — zero matching endpoints exist anywhere in the Postman collection for either.

### Asset Portfolio

- **Endpoints are the Admin CRM "Customer Assets" set, not the deprecated Portfolio Management endpoints and not the Customer Web ones.** Three confirmed endpoints under `/v1/Admin CRM/Customer Module/Customer Assets/`:
  - `GET /v1/customers/:customerId/assets` — list (the mock's table)
  - `PATCH /v1/customers/:customerId/assets/:assetId/review` — verify/reject (the mock's modal actions)
  - `GET /v1/customers/:customerId/assets/:assetId` — single-asset view, **not wired**: the list response already returns full asset objects, so the modal opens off the row already in the query cache, same pattern as [ADR 0019](0019-support-tickets-api-integration.md)'s ticket modal (`tickets.find(...)`), no per-row fetch needed.
  - The `Portfolio Managment (Deprecated)` section's `track-verification`/`one-time-verification` endpoints are explicitly out — that whole module is already marked deprecated in `docs/STATUS.md`.
- **List response shape — the Postman sample was wrong; live-tested and fixed 2026-08-11.** The sample showed `{status, data: {assets: [...]}, message, code, pagination}` (nested at `data.assets`), and the original build matched that literally. Live testing against two real customers (both with real assets) showed the actual endpoint returns a **bare array at `data`** — `{status, data: [...], message, code, pagination}` — consistent with every other paginated list in this codebase, including the sibling `Get a Customer Loan Requests` endpoint. The Postman collection's own sample for this one endpoint was simply stale/incorrect, not a real quirk of the API. Fixed directly in `CustomerAssetsResponseType` (now plain `PaginatedApiResponse<CustomerAssetType[]>`) and `asset-portfolio-panel.tsx`'s unwrap (`response?.data ?? []`) rather than round-tripped back to DeepSeek — a one-line correction matching an established pattern elsewhere in the codebase.
- **Money fields are `{value, currencyCode}` objects** (`price`, `pawnValuationPrice`, etc.), matching the existing `AssetPriceType` in `src/types/asset-management.type.ts` — reuse that type rather than defining a new one, and format via the existing money-formatting utilities already used elsewhere (extract `.value`), not the mock's flat `number` fields.
- **Review payload — three flagged assumptions**, all because the one Postman sample for each case doesn't fully cover what the mock UI collects:
  - `ASSUMPTION` — **"Physical Defects" text field maps to top-level `defectComment`.** The confirmed request body only contains `assetExamination: {dateSubmitted, dateExamined, examinationOfficerRemark, examinationOfficerIdentity, hasCertificationPapers, isBoxPackaged}`, `pawnValuationPrice`, and `status`. It never sends the mock's "Physical Defects? (If Yes, Specify)" text. The asset object schema has an otherwise-unused sibling field `defectComment` (seen as `null` in every sample) whose name is the closest plausible match — sending the collected text there is the best available guess, not a confirmed mapping.
  - `ASSUMPTION` — **"Reason for Rejection" (the reject-step dropdown) also maps to `defectComment`.** No dedicated rejection-reason field exists anywhere in the asset schema (contrast with Loans below, which has a real `rejectionReason` field + a confirmed reasons-list endpoint). Verify and reject are separate, mutually-exclusive request flows in the UI, so there's no collision between these two assumptions in practice — but both are guesses at the same field for two different purposes, and only live testing will show whether either is right.
  - `ASSUMPTION` — **Reject requests can omit `assetExamination`/`pawnValuationPrice` entirely**, sending just `{status: "rejected", defectComment: reason}`. The one confirmed "Mark as Rejected" sample actually replays the *exact same* `assetExamination`/`pawnValuationPrice` values as the verify sample — plausibly just a copy-pasted Postman example rather than a deliberate requirement that reject also needs examination data the reject-step UI never collects. Sending the minimal reject body is the design call; if the backend 400s on a missing `assetExamination`, that's the fix, not a redesign.
  - **All three of the above remain untested as of 2026-08-11.** Every asset visible in the live backend across the customers checked was already `"verified"` (seeded/demo data) — there was no pending asset anywhere to exercise either the verify or reject payload against. Re-test the next time a pending asset exists in the backend.

### Asset Loans

- **Endpoints are the Admin CRM "Loan" set, scoped by customer where the URL allows it:**
  - `GET /v1/customers/:customerId/loans` — list (customer-scoped)
  - `GET /v1/loans/:loanID` — single loan (not customer-scoped — general loan resource)
  - `PATCH /v1/loans/:loanID/reject` — confirmed body `{rejectionReason: string}`
  - `PATCH /v1/loans/:loanID/approve` — confirmed body `{liquidationThreshold: {value, currencyCode}, dateDisburse: "YYYY-MM-DD"}`
  - `GET /v1/loans/rejection-reasons` — confirmed static list (`["Insufficient collateral value", "KYC requirements not met", "Credit risk too high", "Asset verification incomplete", "Requested amount exceeds policy limits", "Duplicate or fraudulent application", "Other"]`) — **replaces** the mock's hardcoded `reasonOptions` (`"Asset Collateral Low"`, etc.), which don't match any real value.
  - `GET /v1/loans/:loanID/schedule` — confirmed, well-sampled (installment-by-installment breakdown), but **not wired**: the current mock UI has no schedule/installment section anywhere in the loan modal, so there's no UI to wire it to. Same "don't build UI nobody asked for" call ADR 0019 made for create-ticket.
- **These four endpoints are shared with the separate, not-yet-built top-level Asset Loans module** (`docs/STATUS.md` row, [ADR 0009](0009-asset-loans.md): "Requests/approve-reject/activity-log endpoints confirmed via Postman... build pending"). Building one shared `loan.route.ts` / `loan.fns.ts` (client) / `loan.queries.ts` / `loan.fns.ts` (mutations) domain now — not nested under `customer.*` — means ADR 0009's future build reuses this instead of duplicating it, the same reasoning [ADR 0019](0019-support-tickets-api-integration.md) used for one shared `reviewSupportTicket` mutation serving two ticket surfaces.
- **`liquidationThreshold` is a money amount, not a percentage — a real correction to the mock's data model, not just a wiring detail.** The mock's `AssetLoan.liquidationThresholdPercent` field and the table's "Liquidation Threshold" column currently render a percent (e.g. `78.2%`). The real API models and the confirmed approve-endpoint payload both use `liquidationThreshold: {value, currencyCode}` — a dollar amount, matching `ltv`/`collateralValue`/`loanValue`. The column must switch from a percent display to a currency display; this isn't optional formatting, the underlying value the mock invented doesn't correspond to anything the API returns.
- **Discovered during build: `loan-case-flow.ts`'s `LoanCaseApprovalPayload` and `customers.schema.ts`'s `loanCaseApprovalSchema`/`assetPortfolioInfoSchema` are shared infrastructure, not exclusive to this tab.** They're also consumed by the still-fully-mocked Smart Contracts tab (`smart-contract-modal-content.tsx`, `smart-contracts-panel.tsx`) and by the separate top-level Asset Loans module (`asset-loans/details/index.tsx`, [ADR 0009](0009-asset-loans.md)), both explicitly out of scope for this round. Same story for `CollateralDetailsCard`/`CollateralValueBar` in `asset-loan-shared.tsx`, which those same two out-of-scope surfaces also render via a legacy flat-prop signature. Correct call made during build: extend these with a `loan?: LoanType`-typed real-data path alongside the existing flat-prop path, rather than deleting/renaming fields those other surfaces still depend on — deleting instead would have broken two modules this ADR explicitly says not to touch. One side effect: `loanCaseApprovalSchema`'s `repaymentDue` validation was loosened from required to fully optional for *all* three consumers (not just Loans), since the schema is shared and only Loans stopped needing the field — Smart Contracts' and the top-level Asset Loans module's own approval forms still show it as a required input in their UI, but the shared schema no longer enforces that. Low risk (both those surfaces are pure mock/local-state with no real backend write), but worth a note for whoever eventually builds those out — this schema needs splitting, not sharing, once any of the other two consumers goes live.
- **The mock's "Repayment Due Date" approval-form field has no home in the confirmed API contract — drop it, don't send it.** The confirmed `PATCH .../approve` request body is exactly `{liquidationThreshold, dateDisburse}`; there's no third field for a repayment due date anywhere in the sample, and the response's `dueDate` is clearly server-computed (disbursement date + `loanTerm`, e.g. `dateDisburse: "2026-08-09"` + a 6-week term → `dueDate: "2026-09-18"` in the sample). The approval form (`LoanCaseApprovalFormValues.repaymentDue`, `LoanCaseApprovalPayload.repaymentDueLabel`) should drop this input entirely rather than collect a value the backend never asked for and silently discard — an admin filling in a date that then vanishes is worse than not asking.
- `ASSUMPTION` — **`:loanID` in `GET /v1/loans/:loanID`, `.../schedule`, `.../reject`, `.../approve` means `loanRef` (the Mongo-style internal ref), not `loanId` (the human-readable `CU-...` value).** The collection only ever shows these as the literal `{{loanID}}` variable — never a resolved example URL, and no test script sets it programmatically — so which field it actually is isn't confirmed either way by the sample data itself. The two other resources in this same collection disagree with each other on this exact question (ticket review keys off `ticketRef`, the Mongo-style ref; asset review keys off `assetId`, the human-readable one), so neither is a reliable precedent to lean on. Defaulting to `loanRef` because it's the more common REST convention for a mutation path param, but this is a guess, not a read of confirmed data — a wrong guess here means every loan action call 404s immediately, which will be obvious the moment it's tested live. **Still untested as of 2026-08-11** — the customers checked live (including the one the Postman samples themselves were captured against) currently have zero open loans in the backend, so there was nothing to click approve/reject on. Re-test the next time a customer has a pending loan.
- **List response follows the standard paginated-array envelope** (`{status, data: [...], message, code, pagination}`, `borrower: {id, name, creditScore, email}` embedded per loan) — confirmed, no assumption needed here, unlike Support Tickets' equivalent endpoint which needed a live check.
- Same local-cache pattern as Portfolio: the loan modal opens off the row already in the list query's cache; `GET /v1/loans/:loanID` isn't wired for the same reason `GET .../assets/:assetId` isn't.

### File structure

- `Asset Portfolio` endpoints are fully customer-scoped (`/v1/customers/:customerId/assets...`) — new dedicated `customer-asset.route.ts` / `customer-asset.fns.ts` (client) / `customer-asset.queries.ts` / `customer-asset.fns.ts` (mutations), parallel to but separate from `customer.route.ts` (kept minimal, core customer CRUD only, same as it is today) and unrelated to the deprecated global `portfolio.*` files.
- `Asset Loans` endpoints are mostly loan-ID-scoped, not customer-scoped — new dedicated `loan.route.ts` / `loan.fns.ts` (client) / `loan.queries.ts` / `loan.fns.ts` (mutations), as its own domain per the sharing rationale above.

## Context

`docs/STATUS.md`'s Customers row lists KYC, Asset Portfolio, Asset Loans, Transactions, and Smart Contracts as still-mocked tabs on the customer detail page. The `luxfi.postman_collection.json` added 2026-08-11 confirms real contracts for Asset Portfolio and Asset Loans (the KYC contracts are also confirmed, but need a UI redesign first — deferred, see Decision). This is the second phase of the sequenced API-integration work that started with Support Tickets ([ADR 0019](0019-support-tickets-api-integration.md)), which itself surfaced two live backend bugs during manual testing — the same live-verification step is planned for this phase before sign-off, given the three flagged assumptions above.

## Alternatives Considered

- **Wire the deprecated `Portfolio Managment (Deprecated)` endpoints** (`track-verification`, `one-time-verification`) instead of the Admin CRM Customer Assets set. Rejected — that module is already marked deprecated in `docs/STATUS.md`; building new integration against it would create work that needs re-doing once it's removed.
- **Treat Asset Loans' endpoints as customer-scoped-only and nest them under `customer.fns.ts`.** Rejected — four of the six confirmed endpoints (`view`, `approve`, `reject`, `rejection-reasons`) key off `loanID`, not `customerId`, and are the exact endpoints `docs/STATUS.md` already earmarks for the separate top-level Asset Loans module. A shared `loan.*` domain avoids rebuilding this when that module is picked up.
- **Guess a single confirmed field for the asset's rejection/defect text instead of flagging two separate assumptions.** Rejected — verify's "Physical Defects" and reject's "Reason for Rejection" are genuinely different UI concepts that happen to have no confirmed backend field each; collapsing the uncertainty into one silent guess would hide that either (or both) could be wrong in different ways once live-tested.
- **Send the full `assetExamination`/`pawnValuationPrice` body on every reject, matching the one Postman sample literally.** Rejected as the default — the reject-step UI never collects examination data, so sending it would mean fabricating values (e.g. today's date, empty officer identity) the admin never entered. Sending the minimal `{status, defectComment}` body is the design call, flagged for live verification like the rest.
- **Keep the mock's hardcoded loan rejection-reason dropdown as-is.** Rejected — `GET /v1/loans/rejection-reasons` is a real, confirmed, low-risk endpoint to wire, and the mock's four options don't match any of the seven real values, so keeping them would mean sending strings the backend has never seen.
