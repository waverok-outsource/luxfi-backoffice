# 18. Marketplace API Integration

## Status

Accepted and implemented — 2026-08-11. Implemented by DeepSeek per `docs/implementation.md`, independently reviewed by Claude against this ADR: `tsc --noEmit`, `eslint`, and `next build` all pass clean; no dangling references to any removed mock type/context/generator remain (verified by grep). Review caught 4 defects in DeepSeek's diff, all fixed directly (small, established-pattern corrections, not sent back for a round-trip) rather than left as follow-up:
- Two call sites (`buy-offer-details-modal.tsx`, `add-to-marketplace-modal/index.tsx`) passed a raw asset-class ID into the shared `AssetDetailsPanel` instead of resolving it via `resolveAssetClassName` — both fixed.
- The P2P Trade modal rendered the missing "Seller Accepted Offer" value as `$0.00` (a hardcoded `0` through `formatCurrency`) instead of `-`, contradicting this ADR's own dash-for-missing-fields decision and the P2P table row's own (correct) handling of the same field. Fixed by widening `OfferSummaryCard`'s `secondaryPriceValue` to `number | null` and rendering `-` for `null`.
- `hasPapers`/`isBoxed` were hardcoded `false` in the Buy Offers knock-on fix instead of using the real values available on `AssetItemType`; fixed for data-hygiene even though currently unused by the panel's layout.

Live manual verification against the real backend (network tab inspection, actual approve/reject round-trips) was not performed in this review pass — it requires authenticated dashboard credentials that weren't available. `next build` succeeding (including static generation of the `/marketplace` route) and the diff matching the confirmed API contracts field-for-field is the verification basis for this sign-off; a live smoke test is recommended before considering this fully done.

## Decision

Wire 5 of the marketplace's 6 tabs to the real backend, using contracts supplied directly by the backend team (Postman-style samples, not a formal OpenAPI spec):

- **LuxFi Listing, Customer Listings, Liquidation Offers, and P2P Trade Requests are one backend resource**, not four. All four map to `GET /v1/asset-market`, filtered by query params (`ownerType=platform|customer`, `listingType=p2p|liquidation`). They share one detail shape, one create endpoint (`POST /v1/asset-market`), and one review/approve-reject endpoint (`PATCH /v1/asset-market/:listingId/review`). The frontend introduces a single `AssetMarketListingType` (`src/types/marketplace.type.ts`) to replace the four separate mock types (`MarketplaceListingType`, `CustomerListingType`, `LiquidationOfferType`, `P2PTradeRequestType`), and a single `useAssetMarketListings(query)` hook backs all four tabs, differing only in the query string each tab sends.
- **Audit Log reuses the existing generic audit infrastructure.** `GET /v1/audits?resource=assetMarket` is the same endpoint already wired for the Customers module's audit log (`useAuditLogs`, `src/services/queries/audit.queries.ts`). No new client/query code — only a new consumer component, copied from `src/module/dashboard/customers/components/tables/audit-log-table.tsx`.
- **Buy Offers is deferred, on mock data, this round.** Its natural backend resource is `GET /v1/orders` (and `GET /v1/orders/:orderId`) — a materially different shape (multi-item orders with `items[]`, payments, settlements) with no review/approve-reject endpoint at all. Redesigning that tab around orders is a separate piece of work; see Alternatives Considered.
- **Server-side pagination and search replace the in-memory `context.tsx` providers.** `MarketplaceListingsProvider`, `CustomerListingsProvider`, `LiquidationOffersProvider`, and `P2PTradeRequestsProvider` (all backed by 1000-row mock arrays with client-side filter/slice) are deleted. This follows the pattern already established by the Customers and Asset Management modules: `useURLQuery` + `convertObjectToQuery` + a React Query hook + React Query cache invalidation on mutation, no page-level context. `BuyOffersProvider` is untouched since Buy Offers stays mocked.
- **A single shared status config** (`ASSET_MARKET_LISTING_STATUS_CONFIG`, keyed by `"pending" | "approved" | "rejected"`) replaces the four separate, slightly-different status enums the mock UI had (`listed/unlisted`, `pending/active/rejected`, `pending/approved/rejected` ×2). The backend's tri-state review outcome is the same for every listing regardless of `ownerType`/`listingType`.
- **Fields the mocked UI implied but the real API does not provide are rendered as `-`, not fabricated or restructured away**, per explicit product direction (2026-08-11): the user wants the gap visible in the running UI so it can be raised with the backend engineer directly, rather than have the frontend quietly redesign around the gap. Concretely:
  - No listing carries an `orderId` (that concept only exists on the separate Orders resource) — every Liquidation Offer / P2P Trade row and modal shows `-` for Order ID.
  - P2P listings (`listingType=p2p`) have no buyer field at all — it's a single-seller listing, structurally identical to every other listing. Buyer Name / Buyer ID render as `-`; "Seller Accepted Offer" (a negotiated second price) also has no backend equivalent and renders as `-`. Only "Initial Listed Offer" (mapped to `listingPrice`) is real.
  - Liquidation Offers *does* have two real, distinct price fields to use (`listingPrice` and `liquidationPrice`), so "Initial Liquidation Offer" / "Seller Offer" map to real data — no dash needed there.
- **Actions with no backend endpoint stay visible but disabled/non-functional**, each flagged as an open backend dependency, rather than removed from the UI:
  - Asset Listing Details modal's Delete / Save Changes / Unlist Asset buttons (no edit/delete/unlist endpoint exists) — kept, disabled, with a tooltip.
  - Buy Offer Details modal's Approve / Reject buttons (no order-review endpoint exists) — kept as-is (matches today's already-non-functional mock behavior).
- **Rejection reason is collected but not sent.** `PATCH .../review` only accepts `{ status: "approved" | "rejected" }` — no reason field. The reject confirmation dropdown stays in the UI for the admin's own workflow/record-keeping, but the selected reason is not included in the mutation payload.
- **Create-listing form drops the fields the backend doesn't accept** (`additionalInformation`, `isBoxPackaged`, `hasCertificationPapers` are not part of `POST /v1/asset-market`'s `{ quantity, price, assetId }` payload) and adds the `quantity` field the backend requires but the mocked form never collected. This is also the more correct model: `isBoxPackaged`/`hasCertificationPapers` duplicate `assetDetails.isBoxed`/`hasPapers`, which are read-only attributes of the underlying asset (from Asset Management), not something chosen at listing time.
- **Marketplace's cross-module dependency on Asset Management mock data goes away.** Each listing now embeds its own `assetDetails` (name, class, images, case/weight, dial colour, papers/boxed) directly in the API response — `resolveAssetItemById`/`getAllAssetItems`/`resolveAssetClassName` (which read Asset Management's `data.ts` mocks) are no longer needed for the four wired tabs. This resolves the issue flagged in ADR 0007 and `docs/STATUS.md` ("Marketplace depends on Asset Management mock data").
- **Aggregate metrics stay hardcoded.** No metrics endpoint was provided; the three `PairedMetricCard` rows at the top of the page are an explicit, separate backend dependency, unchanged by this integration.

## Context

`docs/STATUS.md` names Marketplace API integration as the single highest-impact remaining piece of work in the app — the module has the most elaborate UI (6 tabs, 5 detail modals, approve/reject flows) and was 100% mock-driven. ADR 0007 documented the UI inventory and flagged every endpoint as "unknown." The backend team has now supplied real request/response samples (pasted directly into the working session, not a formal spec document) for: create listing, list/filter listings (4 query-param variants), get listing by id, review (approve/reject) a listing, list audit logs, list orders, and get an order by id.

Investigating those samples against the existing mocked UI surfaced three structural mismatches the ADR 0007 backlog didn't anticipate (because it was written before any real contract existed):

1. Four tabs assumed to need four separate endpoints turned out to be one endpoint with query-param filters.
2. "Buy Offers" was assumed to be a marketplace sub-resource; it is actually the unrelated Orders resource.
3. The mocked UI's negotiation model (two prices, a buyer, an order id) for Liquidation Offers and P2P Trade Requests doesn't exist in what `/v1/asset-market` actually returns — those tabs return the same shape as every other listing, informational reference prices instead of a negotiated pair, and no buyer at all for P2P.

Several of the resulting product questions (how to handle Buy Offers, missing fields, disabled actions, rejection reason) were put to the project owner directly during this session rather than assumed, since they're user-facing behavior calls, not implementation details. Their answers are recorded as the numbered decisions above.

## Alternatives Considered

- **Redesign Buy Offers around the Orders resource this round.** Rejected for now — orders are multi-item and have no review/approve-reject endpoint, making it a materially different (and larger) design problem than the four listing tabs. Deferring keeps this round's scope to the sub-resource that has a clean, confirmed contract; Orders-based Buy Offers becomes its own follow-up ADR when a review endpoint exists or the read-only design is settled separately.
- **Restructure Liquidation Offers / P2P Trade Requests UI to only show fields the API actually returns** (drop Order ID, buyer fields, second price entirely from the layout). Rejected per explicit product direction: the user wants the gap to stay visible in the running UI (as `-`) specifically so it prompts a conversation with the backend engineer, rather than have the frontend silently paper over a contract gap.
- **Keep four separate query hooks/types (one per tab) instead of one unified `AssetMarketListingType` + `useAssetMarketListings`.** Rejected — the backend genuinely has one resource; four parallel types mapping to identical response shapes would be duplicated code with no behavioral difference, purely for cosmetic separation the mock-data era needed but the real API doesn't.
- **Send the rejection reason to the backend anyway, on the theory it might accept/ignore unknown fields.** Rejected — asserting an untested assumption about backend behavior into a mutation payload is worse than clearly not sending a field the documented contract doesn't list; if the backend does add reason support later, it's a one-line change once confirmed.
